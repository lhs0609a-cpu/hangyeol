# 05 · 과금엔진 명세

**이 문서의 로직이 곧 매출이다.** 구현 시 여기 적힌 것과 다르게 만들지 않는다.

---

## 1. 원칙

```
① 등록은 무료. 1차시도 무료. 2차시 진입 시 첫 과금.
② 주기는 학생별로 독립. 28일 고정.
③ 주기 내 수업 0회 → 휴면. 청구하지 않는다.
④ 계산은 학생별, 청구는 강사 단위로 월 1회 합산.
⑤ 선불 이용권. 미납 시 자동 잠금. 독촉하지 않는다.
⑥ 요금은 주기 개시 시점에 고정. 시급 변경은 다음 주기부터.
```

### 왜 첫 과금이 등록이 아니라 2차시인가

등록 시 과금하면 강사가 **등록을 미룬다.** 학생이 붙을지 모르는 상태에서 돈을 내기 싫어 3~4차시까지 자기 자료로 때우고 나중에 등록한다. 그러면 학생이 첫 수업부터 학습노트를 못 받고, 체험수업 팩이 안 쓰이고, 데이터에 구멍이 난다.

**등록을 공짜로 만들어야 첫 수업부터 우리 안으로 들어온다.**

## 2. 학생 상태 머신

```
                  등록
                    │
                    ▼
              ┌──────────┐   이메일 인증
              │ pending  │──────────────┐
              └────┬─────┘              │
                   │ 4차시 도달 &        ▼
                   │ 미인증        ┌──────────┐
                   ▼               │  active  │◄────────┐
              [자료 차단]          └────┬─────┘         │
                                        │               │ 수업 재개
                          주기 내 수업 0회               │
                                        ▼               │
                                  ┌──────────┐          │
                                  │ dormant  │──────────┘
                                  └──────────┘
              강사 결제 실패                    과정 종료
                    │                               │
                    ▼                               ▼
              ┌──────────┐                   ┌───────────┐
              │  locked  │                   │ completed │
              └──────────┘                   └───────────┘
                                              (읽기전용 아카이브,
                                               재등록 시 병합)
```

### 전이 규칙

| From | To | 조건 | 부수 효과 |
|---|---|---|---|
| — | pending | 학생 등록 | 학습노트 매직링크 발송 |
| pending | active | verified_at 기록 | student_activity(kind='verify') |
| pending | pending | 4차시 진입 & 미인증 | **자료 열람 403**, 강사에게 인증 재발송 안내 |
| active | dormant | 주기 종료 시 lesson_count = 0 | 주기 waived_dormant, 새 주기 미생성 |
| dormant | active | 수업 시작 | 그 시각부터 새 주기 개시 + 즉시 과금 |
| any | locked | 강사 invoice 유예 만료 | 강사의 **전체 학생** 자료 잠금. 학생 노트는 읽기전용 유지 |
| locked | 이전 상태 | 결제 성공 | 잠금 해제 |
| active | completed | 강사가 종료 처리 | 읽기전용. 주기 종료 |

## 3. 주기(cycle) 생명주기

### 3.1 개시

```
트리거: lessons INSERT 시 student.current_lesson_no 가 2 가 되는 순간
       또는 dormant 학생의 수업 재개 시

CREATE billing_cycle {
  cycle_no      = 직전 최대 + 1
  period_start  = now()
  period_end    = now() + 28 days
  tier          = teacher.rate_tier          -- 이 시점에 고정
  base_amount   = TIER_PRICE[tier]
  discount_pct  = (강사의 active 학생 수 >= 11) ? 20 : 0
  amount        = floor(base_amount * (100 - discount_pct) / 100)
  status        = 'open'
}
```

### 3.2 활성 판정

주기 종료 시점에 평가한다.

```
활성 = (A) AND (B)

(A) 해당 주기 내 lessons 레코드 >= 1
(B) 해당 주기 내 student_activity 레코드 >= 1

예외: student.current_lesson_no <= 3 인 동안은 (A)만으로 활성 인정
      (학생이 아직 학습노트에 익숙해지기 전 유예)
```

**(B)를 넣는 이유:** 강사가 학생 없이 자료만 열어보는 것과 실제 수업을 구분한다. 동시에 학생이 우리 시스템을 실제로 쓰는지 검증한다.

### 3.3 종료 처리 (일 1회 배치, KST 03:00)

```
FOR each cycle WHERE status='open' AND period_end <= now():

  lesson_count   = count(lessons in [period_start, period_end))
  activity_count = count(student_activity in [period_start, period_end))
  UPDATE cycle SET lesson_count, activity_count, closed_at = now()

  IF 활성판정 == TRUE:
      cycle.status = 'billable'
      student.status = 'active'
      → 새 주기 개시 (period_start = 직전 period_end, 연속)
  ELSE:
      cycle.status = 'waived_dormant'
      cycle.amount = 0
      student.status = 'dormant'
      → 새 주기 생성하지 않음
      → 강사에게 알림: "○○ 학생이 휴면 처리됐습니다. 청구되지 않습니다."
```

> **주의:** 활성 주기의 새 주기 개시는 `period_start = 직전 period_end` 로 **연속**시킨다.
> `now()` 로 하면 배치 실행 지연만큼 주기가 밀려 장기적으로 청구 횟수가 줄어든다.

## 5. 월 1회 합산 청구

### 왜 합산하는가

학생 10명이면 주기 시작일이 10개 다 다르다. 그대로 청구하면 한 달에 카드가 10번 찍혀 강사가 짜증나고, 카드사 이상거래 탐지에 걸리고, 분쟁 시 우리가 불리하다.

### 배치 (매월 1일 KST 00:00)

```
FOR each teacher:
  cycles = billing_cycles
           WHERE teacher_id = T
             AND status = 'billable'
             AND closed_at < 이번달 1일 00:00 KST

  IF cycles 비어있음: SKIP

  total          = sum(cycles.amount)
  credit_applied = min(teacher.credit_balance, total)
  charge_amount  = total - credit_applied

  CREATE invoice {billing_month, total, credit_applied, charge_amount, status='pending'}
  CREATE invoice_lines (cycle 별 1행)
  UPDATE cycles SET status='invoiced'
  UPDATE teacher SET credit_balance -= credit_applied

  IF charge_amount == 0:
      invoice.status = 'paid'; cycles → 'paid'
  ELSE:
      PG 빌링키 결제 요청
```

### 강사 화면 표시

```
8월 청구 47,400원 — 학생 4명
  마리아   14,900원   14→18차시
  미사키   14,900원   22→26차시
  민        7,900원    6→9차시
  루카스    9,700원   3→5차시 (볼륨 할인 적용)
  ─────────────────────────────
  사라      청구 없음  34일간 수업 없음 · 휴면
```

**내역이 투명해야 분쟁이 안 생긴다.** 휴면 학생도 목록에 표시하되 0원으로 명시한다.

## 6. 결제 실패 처리

```
D+0   결제 실패 → invoice.status='failed', failed_at=now()
                  grace_until = now() + 3 days
                  invoice.status='grace'
                  강사에게 알림 (이메일 + 앱 배너)
                  ※ 이 시점에는 아무것도 잠그지 않는다

D+1   재시도 1회
D+2   재시도 2회 (알림 재발송)

D+3   grace_until 경과 & 미결제
      → invoice.status='locked'
      → teacher.billing_status='locked'
      → 해당 강사의 모든 student.status='locked'
      → 강사: 자료 열람 403, 수업 시작 불가
      → 학생: 학습노트 읽기전용 유지 (학생은 잘못이 없다)
              SRS·HVPT·다청은 계속 가능, 새 차시 자료만 차단

결제 성공 시
      → invoice='paid', cycles='paid'
      → teacher.billing_status='ok'
      → student.status 를 직전 상태로 복원
```

**독촉 전화·문자를 하지 않는다.** 다음 차시가 안 열리는 것이 유일하고 충분한 회수 수단이다.

## 7. 크레딧 선충전

```
50만원 충전 → 60만원 사용 가능 (보너스 20%)
30만원 충전 → 34만 5천원 (15%)
10만원 충전 → 11만원 (10%)

· 크레딧은 invoice 발행 시 자동 우선 차감
· 환불: 보너스분 제외한 미사용 원금만 환불 가능
· 유효기간: 24개월
```

목적은 이자 수익이 아니라 **락인**이다. 충전금이 남아 있으면 강사가 떠나지 않는다.

## 8. 엣지 케이스

| # | 상황 | 처리 |
|---|---|---|
| 1 | 주기 중간에 강사 시급 변경 | 진행 중 주기는 기존 tier 유지. 다음 주기부터 적용 |
| 2 | 주기 중간에 active 학생 11명 돌파 | 진행 중 주기는 기존 할인율. 다음 주기부터 20% |
| 3 | 같은 날 수업 2회 | lesson 2건, 주기는 1개. 과금 변동 없음 |
| 4 | completed 학생 재등록 | email_hash 일치 → 기존 레코드 재활성. **cycle_no 이어감, 새 과금 없음** |
| 5 | 학생 이메일 변경 | 새 email_hash. 기존 레코드에 UPDATE (신규 생성 금지) |
| 6 | 강사 탈퇴 | 미납 invoice 정산 후 처리. 학생 노트는 90일 읽기전용 유지 후 삭제 |
| 7 | 학생이 튜터 변경 (Preply) | 강사가 completed 처리. 주기 즉시 종료, 일할 계산 없음 |
| 8 | 배치 실패로 종료 누락 | 재실행 시 period_end 기준으로 소급 처리. `closed_at IS NULL` 로 탐지 |
| 9 | 결제 실패 중 새 주기 도래 | 주기는 정상 개시(open). 잠금은 자료 열람만 막고 주기 계산은 계속 |
| 10 | 강사가 리포트 미제출 | 수업은 인정(lesson 존재). 다만 SRS 적립 없음 → 다음 복습 슬라이드 비어 있음 |

## 9. 테스트 케이스 (필수 통과)

```
TC-01  등록 → 1차시 → 청구 0원
TC-02  2차시 진입 → cycle#1 open, amount = tier 요금
TC-03  주기 내 수업 3회 + 학생활동 2회 → billable
TC-04  주기 내 수업 3회 + 학생활동 0회 (4차시 이상) → waived_dormant
TC-05  주기 내 수업 0회 → waived_dormant, student=dormant, 새 주기 미생성
TC-06  dormant 학생 수업 재개 → 즉시 새 주기 개시
TC-07  학생 4명 서로 다른 주기 → invoice 1건, line 4행, 카드 1회 결제
TC-08  휴면 1명 포함 → invoice 총액에 미포함, 화면에는 0원으로 표시
TC-09  결제 실패 → 3일간 잠금 없음, 3일 후 전체 학생 locked
TC-10  잠금 상태에서 학생 학습노트 접속 → SRS·HVPT 정상 동작
TC-11  crd 50만 충전 후 invoice 30만 → 크레딧 차감, 카드 결제 0원
TC-12  completed 학생 동일 이메일 재등록 → 신규 과금 발생하지 않음
TC-13  active 11명 돌파 시점 → 다음 개시 주기부터 20% 할인
TC-14  배치 2일 지연 실행 → period_start 연속성 유지, 주기 밀림 없음
```

## 10. 관측 지표 (대시보드 필수)

```
· 활성 학생 수 (일별)
· 휴면 전환율 (주기 종료 대비 waived 비율)
· 강사당 평균 활성 학생 수
· 등록 → 2차시 전환율        ← 첫 과금 도달률
· 2차시 → 6차시 잔존율
· 결제 성공률 / 유예 진입률 / 잠금률
· 크레딧 예치 잔액 총합
· 자료 열람은 있는데 학생활동 0인 레코드 수  ← 우회 신호
```
