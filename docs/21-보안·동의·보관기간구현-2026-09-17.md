# 09번 문서의 미구현 항목 구현 — 2026-09-17

16~20번 점검 이후 남아 있던 것 중 **코드로 메울 수 있는 것**을 구현했다.
PG 계약 키·메일 발신 도메인·R2·이미지 제작·교재 전문가 검수는 코드 밖의 일이라 그대로 남는다.

대조한 문서는 09번(보안·개인정보), 02번 G-03(관리자), 04번 §I(API)다.
HVPT·4·3·2·다청은 미구현이 아니라 12번 D-002 로 **뺀 것**이라 대상에서 제외했다.

## 1. 관리자 2단계 인증 + IP 허용목록 (09번 §6)

그동안 관리자 게이트는 `ADMIN_EMAILS` 하나였다. `guard.ts` 주석이 "IP 화이트리스트 + 2FA 는 둘 다 아직 없다"고 적어 두고 있었다.

세 겹으로 바꿨다.

| 겹 | 수단 | 비어 있을 때 |
|---|---|---|
| 1 | 이메일 허용목록 `ADMIN_EMAILS` | 전부 거부 |
| 2 | IP 허용목록 `ADMIN_IP_ALLOWLIST` (CIDR·IPv6 지원) | 주소로는 막지 않음 (화면이 경고를 계속 띄운다) |
| 3 | TOTP 2단계 인증 | **예외 없음.** 등록 전에는 관리자 API 가 열리지 않는다 |

2번만 "비어 있으면 통과" 인 이유: 서버리스에서 관리자가 고정 주소를 갖지 못하는 경우가 흔하고, 비었을 때 막으면 아무도 못 들어가는 문이 된다. 문서가 요구한 "필수" 는 3번이 받는다.

- TOTP 는 RFC 6238(SHA-1·30초·6자리)을 직접 구현했다. 외부 호출이 0건이라 10번 문서가 금지한 종량과금이 생기지 않는다. RFC 시험 벡터로 검증한다 — 우리 코드끼리만 맞춰 보면 인증 앱과 어긋나도 테스트가 통과한다.
- 시크릿은 AES-256-GCM 으로 싸서 저장한다(학생 이메일과 같은 키·같은 형식). DB 덤프 하나로 2FA 가 무력화되면 얹은 의미가 없다.
- 같은 코드를 두 번 받지 않는다. 통과한 30초 칸을 저장해 재사용을 막는다.
- 코드 확인은 계정당 5회/10분으로 막는다. 여섯 자리는 100만 가지뿐이다.
- 승급 세션은 2시간, 로그인 세션과 별개다. 쿠키 `hg_admin`.
- 기기 교체(재등록)에는 **지금 쓰는 앱의 코드**가 필요하다. 없으면 세션 하나를 훔친 사람이 인증 앱을 갈아끼우고 원래 관리자를 잠글 수 있다.
- 등록·확인 화면은 `/admin/security`. 등록 자체는 승급 세션을 요구하지 않는다 — 요구하면 첫 등록자가 영원히 못 들어온다.

## 2. CSP · HSTS (09번 §6)

두 앱 모두 보안 헤더가 없었다. 미들웨어에서 요청마다 건다(`packages/shared/src/security-headers.ts` 한 곳에서 만든다).

- `script-src 'self' 'nonce-…'` — 인라인 스크립트는 이번 요청의 nonce 를 가진 것만 돈다. Next 가 심는 하이드레이션 스크립트가 그것이다. `unsafe-inline`·`unsafe-eval` 없음.
- `style-src` 는 `'unsafe-inline'` 을 남겼다. 06번 디자인 시스템이 인라인 style 속성을 쓰고, 문서가 금지한 것은 script-src 쪽이다.
- `frame-ancestors 'none'` · `object-src 'none'` · `form-action 'self'` · `base-uri 'self'` · `upgrade-insecure-requests`.
- HSTS 2년 · `includeSubDomains` — 학생 학습노트가 note.\* 서브도메인으로 간다. 빠지면 정작 보호할 쪽이 빠진다.
- `X-Content-Type-Options` · `X-Frame-Options` · `Referrer-Policy` · `Permissions-Policy`.

next.config 가 아니라 미들웨어에 둔 이유: next.config 는 Node 가 직접 읽어 워크스페이스의 TS 모듈을 가져오지 못한다. 두 앱에 복사하면 한쪽만 고치는 날이 온다.

nonce 를 쓰면 페이지가 요청마다 렌더된다. 정적 캐시를 잃는 대신 스크립트 주입 경로를 닫았다.

## 3. 우회 의심 목록 (02번 G-03 · 04번 §I · 07번 A-01)

지표 화면에는 "우회 의심 3건" 이라는 숫자만 있었다. 숫자로는 누구를 봐야 하는지 알 수 없고, 알 수 없으면 아무도 확인하지 않는다.

`GET /api/admin/flags` 와 `/admin/flags` 를 붙였다. 규칙 넷은 문서 그대로다.

| 규칙 | 신호 |
|---|---|
| 자료는 열렸는데 학생 활동이 30일간 0 | 자료 잠금이 새는 첫 신호 |
| 한 학생의 자료를 기기 3종 이상에서 열람 | 강사가 기기를 바꿨을 수도 있다 |
| 30일 내 완료 처리 + 신규 등록 5명 이상 | 한 자리를 돌려쓰는 모양 |
| 한 주소에서 강사 계정 3개 이상 | 계정 공유(R1) 신호 |

**제재 버튼을 만들지 않았다.** 두 문서가 같은 문장을 적어 뒀다 — "플래그만. 자동 제재 금지. 사람이 확인한다." 버튼이 있으면 언젠가 눌린다.

응답에 개인정보를 넣지 않는다. 학생·강사 id 와 신호만 나가고, 주소는 해시 앞부분만 보여 준다.

## 4. 학생 개인정보 동의 (09번 §4)

문서가 요구한 절차가 통째로 없었다. 두 개를 따로 받는다.

- **강사 확인** — 학생 등록 화면에 "학생에게 동의를 받았습니다" 체크를 넣었다. 미리 체크해 두지 않았고, 서버도 이 값 없이는 등록을 거부한다. 강사는 남의 개인정보를 대신 입력한다(09번 §5 L3).
- **학생 본인 동의** — 학습노트 첫 진입에서 직접 받는다. 수집 항목·목적·보관기간·철회 방법을 **학생의 모국어**로 보여 준다(ko·en·ja·zh·vi·id·es·de 8종). 동의 전에는 노트의 어떤 화면도 열리지 않는다.

동의 화면은 페이지가 아니라 레이아웃이 가로챈다. 페이지로 두면 새 화면마다 리다이렉트를 붙여야 하고 언젠가 하나를 빠뜨린다. API 쪽은 `requireConsentedStudent` 하나로 막는다.

동의 기록에는 **판 번호**(`CONSENT_VERSION`)를 함께 저장한다. 고지를 고친 뒤 분쟁이 생기면 "동의했다" 는 기록만으로는 아무것도 증명하지 못한다. 판이 올라가면 다시 받는다.

동의 클릭은 `student_activity` 에 남기지 않는다. 남기면 클릭 한 번이 과금 활성 판정의 (B) 조건을 채운다 — 수업도 복습도 없는 주기가 청구된다.

번역은 초안이다. 09번 §5 L3 의 법률 자문에서 문구를 확정한다. 화면에 문장을 박지 않고 `packages/content/src/consent.ts` 한 곳에 모아 뒀다.

## 5. 감사 로그 확대 (09번 §6)

문서는 "자료 열람 · 과금 · 학생 삭제 · 관리자 조회 전건" 을 요구한다. 자료 열람(`asset_views`)과 학생 등록만 남고 있었다.

- 관리자 요청 **전건** — 어떤 경로를 어떤 방식으로 열었는지. 관리자 트래픽은 하루 수십 건이라 비용이 되지 않는다.
- 청구서 생성 · 미납 잠금 — 청구서 행만으로는 어떤 배치가 언제 만들었는지 되짚을 수 없다.
- 2단계 인증 등록·승급, 동의·철회, 파기, 강사 탈퇴.

## 6. 보관기간과 파기 (09번 §4)

보관기간 표가 문서에만 있었다. 문서에만 있는 보관기간은 지켜지지 않는다.

| 기준 | 기한 |
|---|---|
| 학생 철회 요청 | 30일 뒤 파기 + 강사에게 통지 |
| 강사 탈퇴 | 90일 뒤 그 강사의 학생 학습 이력 파기 |

- 철회는 학습노트 하단에서 학생이 직접 요청한다. 누르는 순간 지우지 않는다 — 진행 중인 수업의 진도까지 사라지면 강사는 이유도 모른 채 학생을 잃는다. 요청을 남기고 강사에게 알린 뒤 기한이 지나면 배치가 지운다.
- 강사 탈퇴는 설정 화면에서 이메일을 다시 입력해야 진행된다. 계정은 즉시 막히고(로그인·토큰 갱신 모두), 데이터는 기한에 따라 지워진다.
- 파기는 **학습 이력**(단어장·복습·레벨 테스트·리포트 항목·열람 로그·예정 수업)을 지우고, 학생 레코드의 식별 정보(이름·이메일·국가·플랫폼 주소)를 비운다. **수업·청구 행은 남긴다** — 05번의 계산 근거이고 09번 §5 L2·L4 가 거래 내역 보관을 요구한다. 행을 통째로 지우면 청구서 라인이 사라져 매출 근거가 깨진다.
- `email_hash` 는 NOT NULL 이고 (강사, 해시)가 유일키다. 빈 값으로 두면 두 번째 파기에서 충돌하므로 난수를 넣는다 — 어떤 이메일로도 다시 찾아지지 않으면서 유일성은 지킨다.
- 배치는 매일 돈다(`/api/cron/cycle-close?job=retention-purge`). 기한이 지난 것만 건드리고, 무엇을 왜 지웠는지 감사 로그에 남긴다.

## 마이그레이션

| 이름 | 내용 |
|---|---|
| `20260917000000_admin_2fa` | `teachers.admin_totp_secret` · `admin_totp_enrolled_at` · `admin_totp_last_step` |
| `20260917010000_consent` | `students.teacher_consent_at` · `consent_at` · `consent_version` · `consent_locale` · `withdraw_requested_at`, `teachers.withdrawn_at`, 부분 인덱스 2개 |

운영 DB 적용은 이 작업에서 하지 않았다. 기존 행은 전부 NULL 로 남는다 — 기존 학생은 학습노트를 다음에 열 때 동의 화면을 한 번 보고, 기존 관리자는 `/admin/security` 에서 인증 앱을 한 번 등록한다.

## 배포 전에 해야 하는 것

1. 두 마이그레이션을 운영 DB 에 적용한다.
2. 관리자 계정으로 `/admin/security` 에서 인증 앱을 등록한다. **등록 전에는 관리자 화면이 열리지 않는다.**
3. 고정 주소에서만 관리자 화면을 연다면 `ADMIN_IP_ALLOWLIST` 를 넣는다. 넣지 않아도 2단계 인증은 강제된다.
4. CSP 가 붙은 뒤 두 앱의 화면이 실제 브라우저에서 도는지 확인한다. 정적 검사로는 스크립트 차단을 알 수 없다.

## 검증

- 단위·회귀 테스트 전체 통과(새 검사 포함: RFC 6238 시험 벡터, IP 매칭, CSP 지시문, 동의 관문, 파기 기한·대상).
- 타입 검사, 디자인·라이선스·화이트라벨 게이트 통과.
- 두 앱 프로덕션 빌드 통과.
- 실제 브라우저에서의 CSP 동작, 운영 DB 마이그레이션, 실제 파기 실행은 하지 않았다.
- 동의 문구의 법률 검토(09번 §5 L3)는 남아 있다.
