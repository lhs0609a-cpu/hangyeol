# 교재·강사 운영·결제 구현 점검

이 문서는 개선 전 점검 기록이다. 후속 구현과 실제 검증 결과는 [18번 문서](./18-수강정산교재구현-2026-09-09.md)에 기록했다.

점검일: 2026-09-09. 대상: 현재 로컬 저장소.

판정: 초급 콘텐츠와 운영 기능의 기반은 구현되어 있으나, 왕초보 강사가 바로 유료 서비스를 운영할 수 있는 완성 상태는 아니다. 이전 디자인 작업 완료와 서비스 전체 완성은 구분해야 한다.

## 확인 범위

- 콘텐츠 소스와 실제 export 수량, 강사·학생 화면, API, 코어 서비스, DB 스키마, 배치 설정을 확인했다.
- `npm.cmd test` 재실행: 18개 파일, 285개 테스트 통과.
- 실제 계정 생성, 학생 정보 조회, 카드 승인·취소, 운영 DB 변경은 하지 않았다. 외부 배포 환경의 별도 서비스 유무는 확인하지 않았다.
- 이전 브라우저 검사는 공개 학습 흐름과 일부 모의 API를 검증한 것이다. 실제 DB·결제·메일의 전체 연동 통과를 의미하지 않는다.

## 운영 프로그램

학생 등록·목록·상태 관리, 초대 링크, 수업 시작·리포트, 예약 API, 학습노트·복습, 강사 승인, 관리자 콘텐츠·이미지 관리의 화면 또는 서비스 코드가 있다. 실제 DB를 사용하는 코드도 있으므로 전부 정적 목업인 것은 아니다. 다만 운영 완성 판정을 막는 문제가 있다.

### 우선 수정: 재수행과 수업 시작의 진도 불일치

- `packages/core/src/teaching-plan.ts:185`: 직전 결과가 repeat이면 현재 차시를 다시 안내한다.
- `packages/core/src/lessons.ts:63`: 직전 결과를 확인하지 않고 `currentLessonNo + 1`로 시작한다.
- 리포트 저장은 outcome을 기록하지만 차시를 되돌리지 않는다.
- `apps/teacher/app/lesson/[studentId]/page.tsx`는 시작 API가 반환한 lessonNo로 교재를 연다.
- 따라서 3차시 재수행 안내 뒤 시작하면 4차시 자료로 넘어가는 코드 경로가 있다. 실제 수업 횟수와 학습 단원 진도를 분리하고 재수행 통합 테스트가 필요하다.

### 우선 수정: 요청 본문이 인증된 강사 ID를 덮어쓸 수 있음

- `apps/teacher/app/api/billing/card/route.ts:20` 및 `apps/teacher/app/api/students/route.ts`에서 `{ teacherId: ctx.teacherId, ...body }`를 서비스에 전달한다.
- `packages/core/src/http.ts`의 readJson은 타입 단언만 하므로 추가 필드를 제거하지 않는다.
- 요청에 teacherId가 있으면 서버가 확인한 소유자 값이 덮인다. TypeScript interface는 런타임 검증이 아니다.
- 허용 필드만 명시적으로 전달하고 인증된 ID를 서버에서 고정해야 한다. DB 형변환을 포함한 실제 공격 재현은 하지 않았다.

### 누락: 자동 알림 발송 연결

리포트·결제 실패 시 notification 레코드를 만드는 코드는 있다. 저장소에서 이를 소비해 실제 이메일을 보내는 워커·메일 제공자 연동·발송 재시도 경로는 확인되지 않았다. 예약 레코드 생성만으로 학생에게 알림이 도착하지 않는다.

### 추가 확인 사항

- `teaching-plan.ts` 복습 이행률은 기한 도래 카드 수와 한 번 이상 복습한 카드 수를 합산한다. 두 집합이 겹칠 수 있어 실제 기간별 복습 이행률과 다르다.
- 복귀 수업 시간 배분은 현재 45분 합계인데 화면은 '오늘 50분'으로 표시한다.
- 개발 시드는 15차시 한 건만 DB에 넣는다. 전체 교안은 코드에 있으나 DB의 단원 메타데이터 동기화 절차는 별도 확인이 필요하다.
- 대시보드는 DB 미설정 또는 유효 강사 조회 실패 시 표시된 데모 데이터로 전환된다. 데모 화면 확인을 운영 연동 검증으로 간주하면 안 된다.

## 결제

**실제 결제 완성: 아니오.** 현재 모델은 학생별 사용량을 기준으로 강사에게 플랫폼 이용료를 청구한다. 외국인 학생이 수강 상품을 고르고 강사에게 수업료를 내는 구매·예약·결제·환불·정산 흐름은 저장소에서 확인되지 않았다.

구현된 부분:

- 요금·할인·28일 주기·청구서·크레딧·실패 유예·잠금 계산.
- 강사 청구 내역 조회 화면.
- 빌링키 문자열 저장 API.
- 일반 HMAC 서명 검증과 결제 성공·실패 웹훅 처리.
- 주기 마감, 청구서 생성, 잠금 적용 배치.

빠진 연결:

- PG 결제창/SDK, 카드 등록 발급·인증 흐름, 실제 승인 API 호출 어댑터.
- `/api/billing/credits/topup`은 견적만 반환한다. 결제 세션을 생성하지 않는다.
- 청구서 생성 후 최초 카드 청구 호출이 없다.
- retryInvoice는 외부 charge 함수를 주입받는 서비스일 뿐이다. 호출하는 결제 재시도 작업과 스케줄이 확인되지 않는다.
- `vercel.json`에는 cycle-close, invoice-create, lock-enforce만 등록되어 있다.
- 환불 금액 계산 함수는 있지만 실제 취소·환불 API와 사용자 흐름은 확인되지 않는다.

실결제 연결 전에 수정할 코드 문제:

- 청구서 성공 처리에서 수신 금액과 청구 금액의 일치 검증이 없다.
- CreditTopup.pgTid에 고유 제약이 없고 중복 조회가 트랜잭션 밖에 있어 동시 웹훅의 중복 적립을 확실히 방지하지 못한다.
- 크레딧 잔액을 읽은 뒤 계산된 절대값으로 갱신하므로 동시 충전 간 갱신 유실 가능성이 있다.
- 동일 거래 재전송 일부만 차단하며, 성공 뒤 지연된 실패 이벤트가 도착하는 등의 상태 전이를 추가 검증해야 한다.

## 완료까지의 우선순위

1. 인증된 강사 ID 고정, 재수행 진도, 결제 상태·동시성 문제 수정과 회귀 검사.
2. 초급 70차시 검수, 초보 강사의 첫 수업 연습·수업 중 도움말 동선 연결.
3. 분리된 테스트 DB에서 강사 승인 → 학생 초대 → 수업 → 리포트 → 학생 복습 → 알림을 실제 연동 검증.
4. 강사 이용료 결제와 학생 수강료 결제의 사업 범위를 확정해 필요한 PG·환불·정산 흐름 구현.
5. PG 테스트 환경에서 승인·실패·중복 알림·취소·재시도를 검증한 뒤 운영 설정과 배포 검증.
6. 전체 250차시가 출시 범위라면 나머지 180차시 및 필요한 교육용 이미지·강사 자료 제작·검수.

이번 작업은 점검과 보고서 작성이며, 위 기능을 수정하거나 실결제를 실행하지 않았다.
