# 수강·정산·정규 교재 구현 — 2026-09-09

이 문서는 16·17번 점검 이후 추가 구현과 검증을 기록한다. 운영 배포나 실제 PG 거래·은행 송금 완료를 의미하지 않는다.

## 실제로 연결한 화면

| 사용자 | 주소 | 기능 |
|---|---|---|
| 방문 학생 | 강사 앱 `/courses` | 모집 과정, 총 수강료, 강사, 수업 횟수·시간, 수강 신청, 개인 접속 링크 재요청 |
| 승인된 학생 | 강사 앱 `/student-area` | 개인 수강 주문, 결제 확인, 남은 회차, 미사용 회차 환불, 학습노트 이동 |
| 강사 | `/earnings` | 학생 수강권, 회차별 수강료·수수료·정산액, 송금 확인 기록 |
| 관리자 | `/admin/courses` | 가격·수수료·횟수 설정, 모집 시작·중지, 신청 승인·거절, 정산 대기 생성, 송금 확인 기록 |
| 학생 | 학생 앱 `/coursebook` | 이미 시작한 차시의 어휘·표현·모델·수행 과제, 글쓰기·말하기 자기 점검, 답안 저장 |
| 강사 | 학생 상세 | 입문 14미션과 정규 교재 제출 답안 확인 |

수강료는 플랫폼이 수금하고 운영자가 강사 정산을 확정하는 방식으로 구현했다. 실제 가격과 수수료율은 임의로 정하지 않았다. 관리자가 입력한 후 공개한다. 외부 플랫폼에서 직접 수금하던 기존 학생의 수업 흐름은 수강권이 없을 때 유지한다.

## 결제·회차·정산 규칙

- 신청 승인 시 결제 주문과 수강권이 같은 트랜잭션에서 생성된다. 주문에 총액·횟수·수수료율을 고정한다. 학생이 브라우저에서 보내는 금액으로 주문 가격을 결정하지 않는다.
- 학생은 자신의 수강 주문만 조회·결제·환불할 수 있다. 신규 신청은 이메일을 암호화·해시 처리하고 공개 응답에 개인 접속 링크나 계정 존재 여부를 넣지 않는다.
- 이메일 안내는 발송 대기열에 기록된다. 강사 앱 주소로 향하는 15분 유효 개인 링크는 발송 시 생성한다. 실제 발송은 메일 설정과 발송 작업 실행이 필요하다.
- 수업 시작 시 회차를 예약한다. 미결제·환불 중·소진된 수강권으로 새 수업을 시작할 수 없다. 동일한 미완료 수업 재요청은 회차를 추가로 차감하지 않는다.
- 리포트를 완료한 회차만 정산 대상이다. 금액은 누적 정수 배분으로 계산해 모든 회차의 수강료와 수수료 합계가 원래 총액과 일치한다.
- 미사용 회차 환불은 `총액 − floor(총액 × 시작한 회차 / 전체 회차)`다. 진행 중 수업은 먼저 완료해야 한다. 환불 요청 시 남은 회차를 닫고, 결과가 불명확하면 같은 주문과 멱등키로 재확인한다.
- 외부에서 취소된 금액이 회차와 맞지 않으면 `review_required`로 기록하고 정산을 막는다. 이 상태의 분쟁 조정·회계 정정은 운영자 검토 대상이며 자동 은행 회수 기능은 없다.
- 정산 대기를 생성할 때 완료 회차를 한 번만 묶는다(회당 최대 100개). 실제 은행 송금 후 수취인·금액 확인 체크와 고유 송금 식별자를 입력하면 확인 기록을 저장한다. **은행 자동 송금 기능은 아니다.**
- 카드번호·계좌 비밀번호는 저장하지 않는다. Toss 주문서형 키는 위젯으로, API 개별 연동 키는 카드 결제창으로 연결한다. 자동결제는 별도의 빌링 계약 키를 사용한다.

구현 근거: [Toss 결제·부분 취소 API](https://docs.tosspayments.com/reference), [Toss JavaScript 결제창 SDK](https://docs.tosspayments.com/sdk/v2/js/payment), [Toss API 키 종류](https://docs.tosspayments.com/reference/using-api/api-keys).

## 교재·그림

- 정규 교안·슬라이드 250차시와 입문 14미션을 유지하고, 정규 교재의 학생용 읽기·답안 저장 경로를 추가했다. 학생이 저장한 답안은 진도 통과로 자동 처리하지 않는다.
- 그림 2종(다시 말해 달라고 부탁하기, 하루 일과)을 새로 생성해 PNG 원본·WebP 배포본을 저장하고 두 앱의 교재에 연결했다. 공용 생활 삽화는 총 8종이다.
- 정규 교재는 단원의 내용에 맞는 공용 그림을 선택한다. 250개의 고유 삽화 또는 기존 360개 이미지 카탈로그의 생성 완료를 주장하지 않는다.
- 250차시는 AI 초안이고, 71~250차시는 개별 상황·예문·수행 과제와 공통 지도 틀을 사용한다. 한국어교원 검수·실제 초보 강사 시범수업 검증·전 차시 음원 제작은 완료된 것으로 표시하지 않는다.

## 검증

- 전체 단위·회귀 테스트: **317개 통과**. 수강 주문 소유권, 미결제·소진 차단, 회차 배분, 정산 전 수업 완료 조건을 포함한다.
- 강사·학생 앱 타입 검사와 배포용 빌드 통과. 디자인·라이선스·학생 화면 브랜드 노출 게이트 통과.
- `tools/check-operations-db.ts`: 분리된 PGlite 메모리 DB에 초기·운영 개선·수강료 마이그레이션을 적용하고 **8개 통합 시나리오 통과**. 신청/승인 중복, 미결제 차단, 회차 예약, 리포트 중복, 정산 중복, 미사용 회차 환불, 정규 교재 접근·저장 등을 검사했다. 환불 PG 응답은 함수 안에서 가짜 응답으로 대체했고 외부 요청은 실행하지 않았다.
- 브라우저 수강 관리 검사: **6개 시나리오 통과**. 신청, 두 종류 SDK 호출 경로, 환불 확인, 관리자 정산 기록, 학생 답안 저장, 실제 로컬 API의 비인증 거부를 확인했다. 브라우저의 업무 데이터와 PG SDK는 테스트 응답을 사용했다.
- 결과 파일: `output/design-review/operations-db-results.json`, `commerce-browser-results.json`. 브라우저 스크린샷은 같은 디렉터리에 있다.
- 추가로 **실제 Next API를 이용한 3개 종단 간 흐름도 통과**했다. 별도 메모리 DB에 두 앱을 순서대로 연결하고 실제 신청 폼 → 승인 API → 학생 개인 링크·쿠키 → 결제 확인 API → 수업/리포트 → 정산 → 환불 → 학생 답안 저장 → 강사 답안 조회를 확인했다. 이 검사에서는 업무 API를 가로채지 않았고 PG만 테스트 응답으로 대체했다. 결과는 `live-commerce-results.json`, 실행 도구는 `tools/check-live-commerce.mjs`다.
- 공개 교재의 14미션 전체 진행·저장, 320/390/768/1440px 화면, 학생 복습 실패 후 재시도도 재검증했다. 새 그림을 포함한 46쪽 PDF를 다시 생성했고, 압축본은 약 3.9MB이며 텍스트·렌더링 검사를 통과했다.

PGlite는 [단일 연결 기반 개발용 DB](https://pglite.dev/docs/pglite-socket)이므로 운영 PostgreSQL의 다중 연결 부하·경쟁 조건을 모두 검증한 것은 아니다. 로컬 테스트 URL에는 `sslmode=disable`을 사용하며 운영 DB 설정에 이 값을 복사하지 않는다.

`tools/mock-pg-provider.mjs`는 별도 테스트 프로세스에서만 불러오는 도구다. 앱 코드에서 가져오지 않으며, 명시적인 테스트 실행 환경이 아니면 시작을 거부한다. 실제 운영 서버의 시작 명령에는 이 도구를 추가하지 않는다.

## 운영 활성화에 남은 설정

1. 운영 DB에 `20260909000000_operations`, `20260909010000_tuition` 마이그레이션을 적용한다. 기존 거래 ID 중복이 있으면 먼저 대조해야 한다. 이 작업에서는 운영 DB를 변경하지 않았다.
2. 실제 계약에 맞는 `TOSS_CLIENT_KEY`, `TOSS_SECRET_KEY`, 별도 빌링 키를 설정하고 테스트 계정에서 승인·실패·재시도·취소·웹훅을 검증한다. 해외 카드 지원은 실제 PG 계약 범위에 맞춰 확인한다. 라이브는 `PAYMENTS_LIVE_ENABLED=true`가 필요하다.
3. `TEACHER_BASE_URL`, `NOTE_BASE_URL`, 검증된 발신 도메인·`RESEND_API_KEY`·`MAIL_FROM`·`MAIL_ENABLED=true`와 cron을 설정한다. 비밀키는 서버 환경에만 설정한다.
4. 관리자 계정에서 강사·가격·수수료·수업 일정 안내를 입력하고 모집을 시작한다. 정산 주기와 실제 수취 계좌 확인·은행 송금은 운영자가 수행한다.

재검증: `npm test`, `npm run typecheck`, 두 앱의 `npm run build --workspace @hangyeol/teacher` / `@hangyeol/note`, 세 가지 게이트. DB 도구는 별도 fixture에 PGlite 0.3.2와 socket 0.0.7을 설치한 뒤 Node 24에서 `node --experimental-strip-types --loader ./tools/resolve-ts-loader.mjs tools/check-operations-db.ts`로 실행할 수 있다. 브라우저 도구는 `output/browser-check`에 Playwright를 설치하고 로컬 3217·3218 포트에서 실행한다.
